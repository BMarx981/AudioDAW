# STARTER.md

The "sine wave with a slider" milestone — the smallest project that exercises every layer of the real DAW's stack. Once this works end-to-end on macOS and Windows, the foundation is real and everything else is built on top of it.

## What You're Building

A desktop Flutter app with:

- A single slider (20 Hz – 2000 Hz, logarithmic)
- A play/stop button
- A Rust audio engine running `cpal` that emits a continuous sine wave at the slider's frequency
- Parameter changes flow from Dart → Rust → audio thread via `flutter_rust_bridge` + a lock-free queue

That's it. Resist scope creep. The point is to prove the plumbing.

## Why These Specific Pieces

| Layer | What it proves |
|---|---|
| `cpal` opening an output stream | Audio I/O works on this OS/driver combo |
| Sine oscillator in Rust | DSP runs on the realtime thread without dropouts |
| Lock-free queue for parameter changes | The Dart→Rust→audio path is realtime-safe |
| `flutter_rust_bridge` codegen | The bridge generates correctly and Dart can call Rust |
| Slider driving the engine in real time | Latency is acceptable end-to-end |

If any of these is broken or awkward in the starter, fix it here, not later when there are 50 features layered on top.

## Setup Steps

```bash
# Toolchain
rustup install stable
cargo install flutter_rust_bridge_codegen --version "^2.0"

# Flutter desktop enable (once per machine)
flutter config --enable-macos-desktop
flutter config --enable-windows-desktop
flutter config --enable-linux-desktop

# Create the Flutter app
flutter create --platforms=macos,windows,linux --template=app app

# Create the Rust engine crate
cargo new --lib engine
```

Then configure `engine/Cargo.toml` as a `cdylib` + `staticlib` target so Flutter can link it, and wire up `flutter_rust_bridge.yaml` to point at `engine/src/lib.rs`.

## Rust Side — The Important Bits

### Public API (`engine/src/lib.rs`)

Keep this tiny. Three functions is enough:

```rust
pub fn start_engine() -> Result<()>;
pub fn stop_engine() -> Result<()>;
pub fn set_frequency(hz: f32);
```

These run on whatever thread Dart calls them from — *not* the audio thread. They post messages to the audio thread through a lock-free queue.

### The audio thread (`engine/src/audio.rs`)

This is the realtime-critical code. Rules:

- No allocation inside the callback closure
- No `println!`, no `unwrap()`, no `Mutex`
- Pre-allocate everything (oscillator state, command buffer) at stream-start
- Drain the command queue at the top of each callback, apply changes, then process

The callback closure owns:
- The oscillator state (phase, current frequency, target frequency)
- The consumer end of the SPSC ring buffer

The Dart-callable functions own:
- The producer end of the ring buffer

When `set_frequency` is called, it pushes a `Command::SetFrequency(hz)` into the ring. The audio callback pops it next time it runs and applies it — with a per-block ramp toward the target frequency so you don't get a click. (This is the "parameter smoothing" pattern you'll reuse everywhere in the real engine.)

### Oscillator (`engine/src/osc.rs`)

A simple sine: maintain a phase accumulator in `f64`, advance by `2π · freq / sample_rate` each sample, output `phase.sin() as f32`. Wrap phase at 2π. Done.

This is deliberately the dumbest possible synth — you're not optimizing it, you're proving the path. The real engine will have wavetable/PolyBLEP/etc. but none of that matters until the plumbing works.

## Flutter Side

The Dart wrapper (`app/lib/engine/engine.dart`) should expose:

```dart
class Engine {
  Future<void> start();
  Future<void> stop();
  void setFrequency(double hz);
}
```

Note `setFrequency` returns `void`, not `Future`. The Rust function is fire-and-forget — push to ring buffer, return. No reason to await it from Dart, and awaiting every slider tick would tank UI responsiveness.

The slider widget calls `engine.setFrequency(value)` directly in `onChanged`. Logarithmic mapping: slider value 0.0–1.0 maps to `20 * pow(100, value)` Hz, giving you 20 Hz at one end and 2000 Hz at the other.

## What "Working" Looks Like

1. Launch the app.
2. Press play. Continuous, clean sine tone from the speakers.
3. Drag the slider. Pitch glides smoothly to match — no clicks, no zipper noise, no audible lag.
4. Quit and relaunch. Same behavior.
5. Run on macOS *and* Windows from the same codebase (Linux is a bonus — pulse/pipewire is fussier).

If you hear clicks on slider drag, the ramp isn't working. If you hear dropouts, something is allocating or blocking. If pitch doesn't change at all, the ring buffer isn't being drained. Each failure mode tells you exactly which layer to look at.

## Common Gotchas

- **macOS entitlements:** the app needs microphone *and* audio output permissions in the sandbox config. cpal output alone usually doesn't need mic, but if you hit "no audio device" errors, check `macos/Runner/*.entitlements`.
- **Windows ASIO vs WASAPI:** start with the default WASAPI backend. ASIO requires a vendor SDK and you don't need it yet.
- **Linux:** if you're on a distro using PipeWire, cpal works fine via the ALSA shim. On pure ALSA, exclusive mode can fight with desktop audio.
- **Hot reload doesn't reload Rust.** Changing Rust code requires `flutter_rust_bridge_codegen generate` and a full restart, not hot reload. This will catch you out at least once.
- **Sample rate negotiation:** cpal will pick the device's default rate, which might be 44100 or 48000 or something weirder. Don't hardcode 48000 in the oscillator — read it from the stream config and pass it into the oscillator at init.

## What This Starter Deliberately Doesn't Have

No multitrack. No file I/O. No VST3. No timeline. No mixer. No automation lanes. No project save/load.

Adding any of those before this works smoothly is a mistake. The whole point is a tight feedback loop on the foundation.

## Tests for the Starter

Even at milestone 0, tests come along with the code. They're small, but they set the pattern:

**Rust side** (`engine/src/`):

- `osc.rs` — unit test that 100ms of output at 440Hz / 48kHz has the right zero-crossing count and peaks at ±1.0
- `osc.rs` — realtime-safety test: `assert_no_alloc` around 1000 buffer-renders of the oscillator
- `commands.rs` — ring buffer round-trip test (push from one thread, pop from another, no missed messages)

**Flutter side** (`app/test/`):

- Slider widget test: dragging the slider calls `engine.setFrequency` with the correct logarithmic value
- Use a `FakeEngine` (not the real bridge) — record calls into a list and assert on them

**End-to-end** (`app/integration_test/`):

- Smoke test: launch the app, tap play, assert no exceptions thrown, assert the engine reports a running stream

**CI on the starter:** all three stages should pass in under 90 seconds total. If they're slower than that here, they'll be unbearable later. Keep it tight.

See `TESTING.md` for the full strategy. The starter is a chance to establish the pattern before there's much code to refactor.

## When You're Done

You'll have working knowledge of:

- How to define a `flutter_rust_bridge` API and regenerate it
- How `cpal` opens streams and what the callback contract is
- What a lock-free SPSC queue looks like in Rust (and why it matters)
- How parameter smoothing prevents clicks
- The full Dart → Rust → audio → speakers latency on your machine

That's the foundation. Everything in the real DAW — tracks, plugins, automation, mixing — is "more of this, organized." Same plumbing, more boxes hooked together.
